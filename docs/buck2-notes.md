# Building midnight-node with Buck2

Cargo is the daily driver. CI also builds and tests the tree with buck2, from a
graph generated out of the cargo workspace and committed. This page is what you
need to work with that graph.

## Commands

Use the buck2 release pinned in `buck2/Earthfile` (`BUCK2_VERSION`); anywhere on
`PATH` works. The prelude is bundled with it.

```sh
# The deliverables: node, toolkit, and the on-chain runtime blob
buck2 build root//node:midnight-node-bin root//util/toolkit:midnight-node-toolkit-bin root//:runtime-wasm
# Every test CI runs
buck2 test root//... --exclude ci-infra
# One target in a container, on an arm64 dev box
earth +buck2-test-one --TARGET=root//docs:docs-docs_tests --PLATFORM=linux-arm64
# cargo fmt + clippy, as the PR gate runs it
earth +check-rust --PLATFORM=linux-arm64
```

## Layout

| Path                   | What                                                           |
| ---------------------- | -------------------------------------------------------------- |
| `<member>/BUCK`        | generated by `gen-first-party.py`, one per workspace member    |
| `third-party/`         | every external crate, generated by reindeer                    |
| `wasm-deps/`           | the same for the runtime's no_std closure                      |
| `third-party/fixups/`  | hand-written per-crate fixups, shared by both universes        |
| `third-party/patched/` | `proc-macro-crate`, patched to resolve renames without `cargo` |
| `BUCK`                 | hand-written: the runtime blob pipeline                        |
| `platforms/`           | target platforms and the cache-backed execution platform       |
| `toolchains/`          | rust and C toolchains, and the wasm compiler/linker shims      |
| `scripts/buck2/`       | the generators                                                 |
| `buck2/`               | the Earthfile functions and `buck2-ci.sh` that CI runs         |

## Regenerating

After any change to a `Cargo.toml` or `Cargo.lock`:

```sh
earth +buck2-regen
```

It runs `scripts/buck2/regen.sh` with the pinned reindeer (`REINDEER_REV` in the
`Earthfile`) and writes the result into the tree; commit it. CI's
`+buck2-check-regen` regenerates and fails on any diff. Another reindeer revision
produces a different graph, so regenerate only through the target.

`regen.sh`, in order:

1. `gen-third-party.py` writes `third-party/Cargo.toml`: every external
   dependency of any member, with the features the whole workspace resolves it to.
2. `reindeer buckify` writes `third-party/BUCK`.
3. `normalize-wasm-stub-outdir.py` keeps a stubbed crate's `OUT_DIR` equal to its
   `CARGO_MANIFEST_DIR`, which a polkadot-sdk bump would otherwise leave stale.
4. `gen-wasm-deps.sh` and a second `buckify` do the same for `wasm-deps/`.
5. `gen-first-party.py` writes each member's `BUCK` and removes the `BUCK` of a
   crate that left the workspace.
6. `check-fixups.py` fails if a fixup value that must track `Cargo.lock` is stale.

Both universes seed their lockfile from the workspace's, so they build the
versions cargo builds. Never hand-edit a file marked `@generated`.

## How buck2 differs from cargo

**One feature set per crate.** Cargo picks features per build; buck2 builds each
crate once. The graph uses the features of a whole-workspace `cargo metadata`.
Two feature sets are layered on top, both named in `regen.sh`:

- `LINT_FEATURES` (`runtime-benchmarks,try-runtime`) applies only under
  `root//platforms:lint`, the platform clippy runs on. First-party targets
  `select()` on it; third-party crates get it through reindeer's `-lint`
  platforms (`third-party/reindeer.toml`, `third-party/PACKAGE`). Nothing built
  for another platform sees these features.
- `TEST_FEATURES` covers integration tests with `required-features`. Such a test
  links its own build of the lib with those features on
  (`pallet-midnight-test-utils` for `persist_refcount`).

**Build scripts do not run for first-party crates.** `gen-first-party.py` supplies
what they would have: `ENV_HOOKS` for compile-time env (ledger versions, the
runtime's `OUT_DIR`, the node's version strings) and `SRCS_HOOKS` for non-Rust
inputs (the crate-local `.sqlx/` cache, metadata blobs, graphql schemas).
Third-party build scripts run where a fixup says so.

**The runtime is a second universe.** `wasm-deps/` is the runtime's dependency
closure resolved for `wasm32v1-none` with default features off. First-party
crates in that closure `select()` on `prelude//cpu:wasm32` to swap in the no_std
features and `root//wasm-deps:` deps. A host-side proc-macro can still drag `std`
onto a shared crate, so the affected crates carry an `omit_features` fixup
scoped to wasm32. `root//:runtime-wasm` builds the cdylib for wasm32, then runs
`wasm-opt` and compresses it into the blob the node embeds.

**Tests run from the project root.** Cargo runs a crate's tests from the crate
dir. A test that reads repo files finds the root with
`midnight_node_res::locate_workspace_root()`. A `resources` entry on a test target
does not place a file; it declares an input, so the cached test re-runs when the
fixture changes. Add one in `gen-first-party.py` (`TEST_RESOURCES`) for anything a
test reads outside its own `src/`.

## Adding a fixup

A crate that builds under cargo and not under buck2 usually needs one of these in
`third-party/fixups/<crate>/fixups.toml`:

| Symptom                                             | Fixup                                     |
| --------------------------------------------------- | ----------------------------------------- |
| build script output missing (cfgs, generated files) | `buildscript.run = true`                  |
| build script needs env cargo would set              | `[buildscript.run.env]`                   |
| `env!("CARGO_...")` fails                           | `cargo_env = true`                        |
| `std` leaks into the wasm build                     | `omit_features` under a `cfg(target_arch = "wasm32")` table |
| a file outside `src/` is `include!`d                | `extra_srcs` / `extra_mapped_srcs`        |

Link directives from a build script are honoured by default (`rustc_link_lib`,
`rustc_link_search` in `reindeer.toml`), as cargo does. Say why in a comment, then
`earth +buck2-regen`. A fixup that hard-codes a value derived from another crate's
version needs a check in `scripts/buck2/check-fixups.py`: such a value goes stale
without breaking the build.

## CI

| Job                              | Runs                      | When                                     |
| -------------------------------- | ------------------------- | ---------------------------------------- |
| `buck2 graph matches Cargo.lock` | `earth +buck2-check-regen` | every PR, push to `main`                |
| `buck2 build + test`             | `earth +buck2-ci`         | push to `main`                           |
| `Fomatting and Linting`          | `earth +check`            | every PR, merge queue, push to `main`    |

buck2 keeps no local action cache, so every job goes through a bazel-remote
action cache: the host's shared one via `--BUCK2_CACHE_ADDR`, else a per-job
sidecar. Fork PRs run on GitHub-hosted runners with no shared cache.

**Clippy** is `+check-rust`: `-D warnings` over every first-party target (libs,
bins, unit and integration tests) under the lint platform. The workspace
`[lints]` table is translated to rustc flags for crates that opt in.

**Tests buck2 does not run.** CI excludes the `ci-infra` label, set on tests that
need infrastructure the buck2 job does not provide:

| Test                                                              | Needs                         |
| ----------------------------------------------------------------- | ----------------------------- |
| `partner-chains-db-sync-data-sources` unit tests                  | postgres (testcontainers)     |
| `midnight-primitives-mainchain-follower` unit tests               | postgres (`#[sqlx::test]`)    |
| `partner-chains-cardano-offchain:integration_tests`               | a Cardano node                |
| `midnight-node-e2e:e2e_tests`                                     | a devnet                      |
| toolkit `single_tx`, `hardfork_e2e`                               | docker-compose                |
| toolkit `toolkit_e2e`                                             | a devnet                      |
| toolkit `indexer_e2e`, `indexer_show_wallet_e2e`                  | a live indexer                |
| `sc-partner-chains-consensus:verifier_network`                    | `substrate-test-runtime` wasm |

Two crates have no unit-test target at all, for the same `substrate-test-runtime`
reason: `sc-partner-chains-consensus` and `sc-partner-chains-consensus-aura`.
The cargo jobs still run every test listed here.

## A local action cache

A bazel-remote in buildkitd's network namespace gives a checkout warm rebuilds.
An earth `RUN` step sees neither the host's loopback nor published ports, but a
container sharing the buildkitd's namespace answers at the sandbox gateway:

```sh
mkdir -p ~/data/bazel-remote
docker run -d --name bazel-remote --restart unless-stopped \
  --network container:earthly-buildkitd --user "$(id -u):$(id -g)" \
  -v ~/data/bazel-remote:/data buchgr/bazel-remote-cache:v2.6.1 \
  --dir /data --max_size 40 --grpc_address 0.0.0.0:9092 --http_address 0.0.0.0:8080
earth +buck2-ci --RUN_ID="$(date +%s)" --BUCK2_CACHE_ADDR=grpc://172.30.0.1:9092
```

`BUCK2_CACHE_ADDR=grpc://172.30.0.1:9092` in a gitignored `.arg` at the repo root
saves passing the flag. `buck2-ci.sh` prints which cache it connected to.
